DeviceMonitor

Open source, MIT

A network monitor for iPhone, iPad and iPhone Duo. It finds the devices on your Wi-Fi, keeps checking whether they answer and tells you when something changes. There is no account, no ads and no location access, and everything stays on the phone.

Role
Solo developer
Stack
SwiftUI, SwiftData, Foundation Models, Swift Charts, Metal

Source on GitHub

What it does

DeviceMonitor scans the subnet, up to /22, with short TCP connection attempts, and uses ICMP and UDP for devices that refuse connections. It browses 28 Bonjour service types, so an AirPlay speaker or a printer shows up under the name you know. It recognises 13 kinds of device and keeps one identity per device across IP changes, so nicknames and notes are never lost.

Each device page charts latency and jitter over the last hour, 6 hours or 24 hours, with gaps left as gaps. Insights gives a security score from 0 to 100 with a checklist of what to fix. On supported iPhones, Apple Intelligence explains each device in plain language without sending data to the cloud.

Only what an iPhone can measure

One dropped packet is never an alarm.

A device turns Unstable on a missed check and Offline only after the number of misses you choose. It needs repeated answers to come back. iOS suspends apps, so the history counts the outages the app saw while it was open. It never shows a percentage over a span it could not watch.

What an iPhone app cannot do

  • Watch the network in the background. iOS suspends apps. Monitoring runs while the app is open, and Activity shows what changed.
  • Read MAC addresses through ARP. That needs a restricted entitlement. Vendor and kind come from Bonjour, hostnames and ports instead.
  • Scan networks larger than /22. Too slow and too costly for a phone. Important devices can be added by address.

How it is built

The monitoring engine runs in an actor. Its events are coalesced on the main actor and written to SwiftData every 500 ms, with a versioned schema migration. Views only read immutable snapshots, never the database. The logic that decides status, schedules checks and computes latency statistics sits in pure, unit-tested functions.

Names and services from the network go to the on-device model as fenced data, to guard against prompt injection.

Current state

Public under the MIT licence. It began as my final project at Grit Academy, where it earned a Distinction, and I have kept developing it as my own app. GitHub Actions builds and tests it.
