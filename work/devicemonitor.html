DeviceMonitor

My degree project: a network-device dashboard with status history, filtering and a detail view, built around three boundaries — a mock service behind a protocol, SwiftData storage with actor-safe fetch and save, and SwiftUI views observing one view model.

What it does

DeviceMonitor is an iOS prototype for monitoring network devices. The dashboard shows online and offline counts in a network overview card, a sticky status filter, search by device name or IPv4 address, and a detail view with metadata and status history. Devices can be added by hand, where they start as pending until the first resolution, and removed with a swipe for the current session. Add, overview and detail are full-screen modals built from shared components.

The app intentionally uses mock and local data only. A mock monitor service produces device snapshots with stable identities and simulated status changes, so the project demonstrates architecture rather than production networking.

The decision

Mock data behind a protocol: the point is to demonstrate the architecture, not the network.

The project is built around three boundaries. The service layer is a protocol with a mock implementation that could be replaced by real scanning. The storage layer wraps SwiftData and owns the merge rules: each snapshot removes stale devices, preserves the ones the user added, matches an existing device by IP address when the service hands out a new ID, and appends to the status history only on a transition. The view layer is SwiftUI observing one @MainActor view model that coordinates the other two. The whole target compiles with Swift 6 and strict concurrency set to complete.

The tests sit on the merge rules, because that is where the bugs would live: filtering and counters, stale-device removal, user-added device preservation, status history only on transitions, IP-based identity when service IDs change, and a manually added device starting as pending. Two XCUITests check that the app launches with its title and measure launch performance.

What I would do differently

The CI workflow builds the app and runs the unit-test target only; the two UI tests run locally in Xcode. That is the first thing I would change. The second is the deployment target: the controls use the iOS 26 segmented picker and Liquid Glass where it fits, and the target is iOS 26.2, so the prototype runs only on the newest release. And a swipe removal lasts only for the current session, which is honest for a demo but is the kind of edge a real device list would have to persist.

Current state

The repository is public under the MIT licence, with one commit (a5fca56, 17 August 2026). GitHub Actions builds the app and runs the unit tests on an iPhone 17 simulator on every push and pull request to main. Previews use an in-memory SwiftData container so they stay isolated from the running app's store. The app ships no real networking and is aimed at demo and prototype scenarios.
