MetalVisualKit

A Swift package of GPU-backed SwiftUI views: a compute-shader particle loader and an ARKit LiDAR point-cloud renderer that samples the camera image per point. SwiftUI owns the view lifecycle; Metal owns the per-point work.

What it does

MetalVisualKit is an MIT-licensed Swift package with two components, both exposed as SwiftUI views. ParticleProgressView and ParticleSpinnerView update about 1 400 particles in a Metal compute shader and draw them as premultiplied point sprites in one draw call. Swift prepares a compact uniform struct and encodes the compute and render passes; it never loops over particles. The loader publishes its percentage to VoiceOver, and both components respect Reduce Motion.

LiDARPointCloudView binds ARKit's sceneDepth map as a texture to the vertex shader instead of reading it back. A 256×192 depth map gives roughly 49 000 vertices per frame; each one samples its depth pixel, unprojects through the inverse camera intrinsics and transforms to world space with the camera pose, all on the GPU. Camera colour comes from the same frame's capturedImage, converted from YCbCr in the shader, with depth and confidence modes kept for diagnostics. Without a LiDAR scanner, and in the Simulator, the view falls back to a procedural cloud.

The package ships with DocC, an example app in a committed workspace and a CI workflow that builds the package, runs the tests, builds the documentation archive and the example app, and runs static checks on every push to main. A script compares the Swift and MSL declarations of every shared struct, and the pipeline tests pin the resulting strides.

The decision

Keep the public API as SwiftUI views, not Metal objects. Someone using the package should never need to meet a compute encoder.

The question I wanted to answer was how much frame-by-frame work could stay on the GPU without turning the public API into a Metal project. So the host app sees progress values, a surface style and a label colour, and the package keeps the device, the pipelines and the buffers to itself. The cost is that the uniform struct layouts are mirrored by hand between Swift and MSL, and editing one side without the other produces a visual glitch rather than a crash. That is why the parity script and the stride tests exist and run in CI.

What I would do differently

Put the physics in real units from the first commit. The first loader pass integrated velocity per frame, so damping depended on the frame rate and the completion burst emptied twice as fast at 120 Hz; moving to pixels per second then left the sprite styling reading the old per-frame scale, which saturated the speed-stretch term and inflated every particle. The point cloud had the same class of bug: a sprite size of 900 layout points put every one of the 49 000 points at the 22 px ceiling, so the setting meant nothing and the fragment overdraw was large. Both fixes are in the changelog; the lesson is that a unit convention is an API, and it needs a test.

Current state

Nothing is tagged yet, so the package installs from the main branch. Xcode 26.6 builds the package, the test suite, the example app and the DocC archive, and both components render in an iOS 26.5 simulator. Live LiDAR has been exercised on a compatible device; the updated portrait transform still needs a fresh device regression pass before a first release. The point cloud visualises the current depth frame and does not accumulate a scan. The unreleased Spatial Scan work adds All, Balanced and Precise confidence floors, explicit Start, Pause, Resume and End states, bounded pinch zoom and VoiceOver zoom actions. The roadmap continues with RoomPlan capture and export, then a custom reconstructed mesh.
